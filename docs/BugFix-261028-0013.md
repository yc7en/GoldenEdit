# BugFix-261028-0013 · 懒填充队列跨文档残留，切到大文档首屏被拖后数秒

## 缺陷描述

性能验收三档连跑时，第三档（8MB）的墙钟时间毫无道理地高：

```
large-8mb.md   墙钟 9819ms  预算 2000ms  FAIL
分段：防抖 153 + 投递 1 + 传输 397 + 建 DOM 9 + 回调 1 = 561ms，未归因 9258ms
```

内核只有 461ms、建 DOM 只有 9ms，却有 9.3 秒挂在「消息在两岸之间排队」上。
单独跑同一档（`PERF_ONLY=large`）只要 757ms。

## 根本原因

分片模式（200KB–2MB）下，首屏只渲染 200 块，其余块先放占位，用 `requestIdleCallback`
一批 40 块慢慢向 Worker 要 HTML。2MB 样本有 13736 块，也就是一万三千多个填充任务排队。

`Pipeline.render()` 换新内容时**没有清掉这个队列**：切到 8MB 文档后，旧文档的填充任务继续
跑，把 Worker 和主线程占满；新文档的 `doc` 消息只能排在后面，等前一批任务啃完才被处理。
于是「首屏被拖后」的那段时间，全部落在探针的「未归因」里。

同一处还有个小问题：`enqueue()` 用 `this.enqueue(this.idleQueue.shift())` 来实现「还有剩就
再排一批」，会把刚取出的那一个键重新塞回队列，造成同键填充两次（第二次被 `data-lazy` 判定为空操作，
但白白多一次 Worker 往返）。

## 修复方法与实现

- [frontend/preview-shell/pipeline.ts](file:///j:/CODE/GoldenEdit/frontend/preview-shell/pipeline.ts)：
  - `render()` 开头清空 `idleQueue`、断开尾部间隔器的 observer——新内容作废旧内容的后台工作；
  - 抽出 `scheduleIdle()`：一批 40 块跑完只在队列非空时重排，不再靠「先 shift 再 enqueue」；
  - 批量填充改为 `void this.fill(k)`，不留下悬空 Promise。
- [frontend/src/perf.ts](file:///j:/CODE/GoldenEdit/frontend/src/perf.ts)：新增 `settle()`，
  每档样本前把预览打回空白文档，验收从干净状态起跑。
- `scripts/perf-check.mjs`：**一档一个进程**。同一个进程里连跑，前档的懒填充仍可能压住后档，
  而验收要回答的是「打开这么大的文件要多久」，每档必须独立计量。

## 影响范围

- 修复前：从 2MB 文档切到更大文档（或任何「占位块很多」的文档之间切换）时，首屏会被上一份
  文档的后台填充拖住，表现为「切文件后预览半天不动」。
- 修复后：切档即作废旧任务；8MB 单档墙钟 733ms（预算是 2000ms）。

## 验证方式

1. `node scripts/perf-check.mjs`：三档墙钟与分段相加应基本吻合，未归因在 100ms 以内；
2. 连续打开 2MB → 8MB 两份文档，观察第二份的首屏与单独打开时相当；
3. `PERF_ONLY=large node scripts/perf-check.mjs` 与整轮里 large 的数字应接近（差异 < 200ms）。
