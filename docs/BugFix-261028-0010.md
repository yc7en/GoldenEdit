# BugFix-261028-0010 · `bus.on('render')` 自激，形成无限重渲染

## 缺陷描述

给 `rendered` 消息补上 `chars`（Worker 实际解析的字符数）之后，性能验收出现一组不可能的数据：

```
medium-2mb.md   字符 1202977→1202977→7   块
large-8mb.md    字符 4828235→4828235→7   块
```

提交了 120 万字符、Worker 只解析了 7 个字符、只产出 7 个块。在此之前这个问题是**隐形的**：
探针只比对「墙钟 vs 预算」，7 个块的渲染当然很快，于是 2MB/8MB 两档一直是假 PASS。

## 根本原因

`editor/index.ts` 在 `onDidChangeModelContent` 里 `bus.emit('render')`，意思是「文档变了，请重渲染」。
但 `main.ts` 里 `bus.on('render')` 的处理是 `preview.push(text)` —— 推文档进预览。
预览渲染完又会走一遍 UI 更新链路，把新的文本再推一次。

也就是说：

1. 每次输入 → `render` → 推预览 → 渲染完成 → 再来一次；
2. `PreviewHost.push()` 里有 150ms 防抖，这个自激循环**用自己制造的推送把上一次推送清掉**，
   所以外部看起来「没在渲染」，实际上下一次推送永远在把上一次覆盖掉；
3. 探针的 `pushAndWait` 最终消费到的，是启动文档那次渲染的 `rendered`（7 个块）。

## 修复方法与实现

- [frontend/src/editor/index.ts](file:///j:/CODE/GoldenEdit/frontend/src/editor/index.ts)：
  内容变更改为 `bus.emit('doc-text')`，语义就是「文档文本变了」，不再借用 `render`。
- [frontend/src/store.ts](file:///j:/CODE/GoldenEdit/frontend/src/store.ts)：事件名补 `'doc-text'`。
- [frontend/src/main.ts](file:///j:/CODE/GoldenEdit/frontend/src/main.ts)：预览的推送订阅 `doc-text`；
  `render` 只保留「界面需要重画」的语义。

两个事件分离之后，`render` 不再能触发推送，自激回路被切断。

## 影响范围

- 修复前：任何一次编辑都会让预览陷入「不停推送自己」的循环，CPU 白烧，且外部无法判断预览是否是最新的。
- 修复后：2MB 从 7 块恢复到 13736 块、8MB 恢复到 54644 块，探针数据才第一次是真的。

## 验证方式

1. `node scripts/perf-check.mjs`；
2. `字符 x→x→x` 三段数字必须相等（不相等会直接标 `MISMATCH`）；
3. 手打一段文字，观察状态条的块数随之变化，且不再出现「预览一直不更新」。
