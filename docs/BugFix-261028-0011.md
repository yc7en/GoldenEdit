# BugFix-261028-0011 · table-gfm 的 `splice` 造成 O(n²)，8MB 内核 3.2 秒

## 缺陷描述

性能验收里 8MB 样本墙钟 4.3 秒、内核 3.3 秒，超预算一倍多。分阶段计时显示全部在解析阶段：

```
内核 3340ms（解析 3187 + 块 153）
```

再往下加规则级计时（`rules` 字段）才定位到具体是谁：

```
core:plugin-hooks = 3092ms    ← 全在这
block:container   =   52ms
inline:delimiter  =   11ms
core:obsidian-callout = 4ms
```

`core:plugin-hooks` 是「依次把 token 流交给各插件的 core 规则」那一段，8MB 样本里有 73 万个 token。

## 根本原因

`plugins/table-gfm/entry.js` 的 core 规则原本这么写：

```js
for (let i = 0; i < state.tokens.length; i++) {
  if (state.tokens[i].type === 'table_open') {
    state.tokens.splice(i, 1, open, ...mid, close);  // ← 每张表都改数组长度
    i += mid.length;
  }
}
```

`splice` 每调一次就把后面所有元素整体前移/后移。样本里有数千张表、七十多万个 token，
于是复杂度是 `表数 × token 数`——体量小的时候毫无察觉，8MB 时直接 3 秒。

## 修复方法与实现

改为**单遍重建**，只分配一个新数组，不再原地搬移：

- [plugins/table-gfm/entry.js](file:///j:/CODE/GoldenEdit/plugins/table-gfm/entry.js) 与
  [frontend/plugins/table-gfm/entry.js](file:///j:/CODE/GoldenEdit/frontend/plugins/table-gfm/entry.js)
  同步重写：遍历一遍，命中表头就把展开后的 token 依次 `push` 进新数组，其余原样 `push`，
  最后整体赋值回 `state.tokens`。

复杂度从 `O(表数 × token 数)` 降到 `O(token 数)`。

## 影响范围

- 只影响 table-gfm 这一条 core 规则；其余插件未在热路径上做数组搬移。
- 修前 / 修后（8MB）：内核 3253ms → 446ms，其中解析 3187ms → 380ms。

## 验证方式

1. `node scripts/perf-check.mjs`，看 `large-8mb` 的「规则耗时」一行——`core:plugin-hooks` 应在 15ms 量级；
2. 打开含多张表格的大文档，表格渲染结果与修前一致（表头 / 对齐 / 单元格内容都不变）。
